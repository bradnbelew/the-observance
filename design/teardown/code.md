# Teardown — CODE dimension (will-it-actually-run)

Read of the real code, not the guides. Verdicts: KEEP / CUT / FIX / SIMPLIFY / REDESIGN.
Worst first. Every finding names the artifact.

---

## 1. [FIX] `discord/src/db/repo.ts:getOpenPuzzles` — `requires_flags` is never selected or AND-tested. The entire gated back-half of the game is wide open.
The seeds (`metapuzzle_seed.sql`, `progression_seed.sql`, `puzzles_seed.sql`) author ~8+ rows whose ONLY gate is the `requires_flags` column (`iss_caught`, `bound_word_known`, `threshold_open`, `true_coord_known`, `seventh_named`, `seventh_suspected`, `undercroft_open`). `getOpenPuzzles` selects `puzzle_key,title,accepted_answers,outcome_type,outcome_payload,movement,active,max_attempts` — **no `requires_flags`** — and `matchPuzzle` only checks `active=true` set-membership. **Blast radius:** every back-half row that ships `active=true` + `requires_flags` (the intended pattern, e.g. `base-docket-reread-auto` gated on `iss_caught`, the Nether/End payoffs gated on `undercroft_open`/`seventh_named`) is solvable on day one before its flag is ever set — the M1→M5 progression collapses; the metapuzzle and the Liar-engine AUTO duplicate are spoofable from the first session. The Java twin `OracleResolver.firstMatch` has the identical gap. **Fix:** add `requires_flags` to the select in BOTH `getOpenPuzzles` (TS) and `SupabaseClient.fetchOpenPuzzles` (Java `select=`), and in `matchPuzzle`/`firstMatch` read `arc_state.flags` once per resolve and reject any puzzle whose `requires_flags` keys aren't all truthy. This is gated on migration 0006 existing (see #2).

## 2. [FIX] `discord/supabase/migrations/0006_*.sql` — does not exist; the `requires_flags` column the seeds and (future) gate depend on is never created.
Both `metapuzzle_seed.sql` (L111) and `progression_seed.sql` (L215) wrap their activation-lane `UPDATE`s in a guarded `if column exists` block that **silently `raise notice` and skips** when 0006 is absent. So today: the column doesn't exist, the guarded UPDATEs no-op, and every gated row that ships `active=true` is fully open (compounds #1); every gated row that ships `active=false` is **permanently dead** (nothing else flips it active). There is no NPE — the guards swallow it — which makes the failure invisible: the seeds "succeed," the game is silently broken. **Fix:** write `0006_requires_flags.sql` adding `puzzles.requires_flags jsonb not null default '{}'::jsonb`, then re-run both seeds so the activation UPDATEs actually land.

## 3. [FIX] `plugin/.../BeatQueuePoller.java` + `SupabaseClient.markBeatDecided` — double-fire window: a beat is enacted in-world BEFORE its status is durably flipped, and the only cross-poll guard is an in-process `Set`.
Flow: `pollOnce` (async) fetches `status=approved`, adds id to `inFlight`, hops to main, enacts (world mutation), THEN schedules an async `markBeatDecided`. The next poll cycle can run while a beat is still mid-enact-or-mid-PATCH: `inFlight` covers it *within one JVM*, but the DB row is still `approved` until the async PATCH lands. If `markBeatDecided` fails its first attempt it is only **queued** (offline queue), and `flushOfflineQueue` stops on first failure — so under a flaky Supabase a beat can be re-fetched and **re-enacted** on the next poll (the comment at L198 admits this is the replay risk). For RevealBeat/SmallStructureBeat this means a structure pasted twice; the FAWE `world_paste_ledger` (`claimPasteLedger`) covers *single-paste set-pieces* only — RoomSwap, NamedMob, KeeperNpc, unlock/toast beats have **no durable idempotency** and will double-fire on a restart-during-poll. **Fix:** PATCH the row to an intermediate `firing` status *before* enacting (claim-then-act), or gate enact on `markBeatDecided(approved→firing)` returning a row; only enact on the winning claim.

## 4. [FIX] Showrunner offline / model offline — the showrunner is a one-shot cron (`run.ts`) with NO catch-up; a missed tick is a permanently-skipped drip, and there is no liveness alarm.
`run.ts` does `snapshot → decide → apply` once and `process.exit`. `decide.ts` drip cadence is `nowMs - lastDripAtMs >= effectiveDripInterval` — if the cron host is down across a window, the *next* tick still drips only ONE node (it doesn't backfill the missed ones), so a multi-hour outage silently stalls the clue feed and nobody is paged. Worse: the gates (`computeAutonomyGates`) and customs/autonomy passes are each independently try/caught to "fail to neutral," so a half-failed tick can advance `last_drip_at_ms` (in `apply.ts`) while the gate computation silently returned empty — the arc keeps its cadence anchor but skips the difficulty/prologue logic with no signal. There is no LLM in this spine (good — it can't be "model offline"), but there's also no heartbeat staleness check anywhere that fires if `last_run_iso` ages out. **Fix:** add a `last_run_iso` staleness alarm to the dashboard health view, and on a drip-due tick where >N intervals elapsed, either drip a small burst or log a loud `warn` the operator sees.

## 5. [REDESIGN] The 11 specscheck-unclassified rows — these are NOT all "merely unregistered." Triage:
- **`a1z26-tick-stave`** (active main_beat): resolves fine at runtime — distinct accepted answers, sets `rosetta_known`, fires unlock at `first_marker_01`. Its ONLY problem is coverage-registration (not in `NON_CIPHER_KEYS`/`CLUE_SPECS`). **Unregistered, not broken.** It is a *number* (tick-stave) cipher though — if it's meant to forge a card, it needs a real `CLUE_SPECS` entry or the drip card forge (`forgeDripCard`) will throw and fall back to the generic report line.
- **`reckoning-rosetta`, `base-docket-reread-auto`** (active): the seed comment itself (L1003) says these MUST be added to `NON_CIPHER_KEYS` or coverage fails — **this is exactly why specscheck is RED.** Runtime-fine, registration-missing. **Unregistered.**
- **`name-where`, `record-url`, `difficulty-mara`, `reckoning-rosetta`** are pure `lore`/`dead_end`/observation rows with no forge spec. Genuinely just need `NON_CIPHER_KEYS` membership.
- **`record-url`** is a genuine hazard: its accepted answer `the record keeps` (L955) is a 3-word generic token. `matchPuzzle` is whole-string so it won't collide with `difficulty-mara`'s longer line, but `the record keeps` is plausibly typeable by accident in `#the-record` scanning → an unintended `lore` reveal. **SIMPLIFY:** drop the bare `the record keeps` mirror; keep only the full-sentence forms.
- **`forged-eighth`, `fork-light`, `fork-name`, `prophet-wall-comfort`, `prophet-wall-name`** — these are referenced in `thread_cards.sql`/`metapuzzle_seed.sql` as thread/fork surfaces but have no registered forge spec; whether they mis-fire depends on whether they ship `active=true` without a `requires_flags` gate (see #1) — if so they're open early. **Verdict:** classify each into `NON_CIPHER_KEYS` (lore) or give a `CLUE_SPECS` entry (cipher); none are "fine to leave unclassified" because specscheck is the build gate and it's RED.
**Net:** of the 11, ~0 will *mis-resolve* on their own (whole-string matching is safe), but ALL 11 keep the build RED, and the ones gated only by the absent `requires_flags`/0006 are open-early (the real bug is #1/#2, surfaced through these rows).

## 6. [FIX] `AnswerNormalizer.java` / `normalize.ts` — normalizers agree, but the documented "minus is dropped" rule silently breaks every coordinate answer, on BOTH surfaces identically.
Both strip `-` to a space: `-1280` → `1280`. The Java doc (L17) and TS both intend this. So a carved coordinate clue whose plaintext is a negative coord can never be matched unless the seed's `accepted_answers` ALSO store the sign-stripped form. This isn't TS-vs-Java drift (they match) — it's a **spec trap**: the `reckoning-rosetta`/coord-literacy thread teaches players to read `-`/`.`/`,` digit glyphs, but the normalizer destroys exactly those marks. **Fix:** confirm every coord/number puzzle's `accepted_answers` is pre-normalized to the digits-only form (seedcheck enforces normalization, but verify the AUTHOR didn't seed `-1280`), and add a seedcheck assertion that no accepted_answer contained a stripped `-`/`.` that changes meaning.

## 7. [KEEP] TS resolver `resolveAnswer` vs Java `OracleResolver.resolveWorldInner` — the idempotency + replay logic is genuinely sound and the two surfaces match.
`recordSolve` (TS upsert `ignoreDuplicates` on `(puzzle_key,player_id)`) and `insertSolveIfNew` (Java POST `resolution=ignore-duplicates,return=representation`, body-length test `> 2`) are the SAME guard and both correctly gate the reward on a genuinely-new row. The per-puzzle cap boundary math is deliberately reconciled (Java subtracts 1 for the just-logged attempt to match the bot's "count prior" semantics — L144). The rate-limit fail-OPEN on DB error is consistent. **Keep this; it's the strongest code in the build.** One nit (FIX): the Java `inserted = b.trim().length() > 2` test is brittle — a PostgREST response of `[ ]` (with whitespace) or a single-row body with a tiny representation could misjudge; prefer parsing the JSON array length.

## 8. [FIX] `apply.ts` drip + `decide.ts` `lastDripAtMs` — a CONFIRM-mode staged drip advances `last_drip_at_ms` immediately, so if the dashboard never approves it, the cadence clock keeps ticking and the NEXT node is staged on schedule — pending drips pile up unposted.
In `applyDecision`, the `d.staged` branch pushes to `pending_drips`, marks `dripped_keys`, AND sets `state.last_drip_at_ms = snapshot.nowMs`. `decide.ts` then won't re-drip until the interval elapses — but it WILL drip the *next* node when it does, regardless of whether the human ever approved the prior staged one. Result: in CONFIRM mode with an inattentive operator, `pending_drips` grows unbounded and the player sees nothing while the engine thinks it's pacing correctly. **Fix:** don't advance the cadence anchor on a *staged* drip; advance it only when the dashboard actually posts (or cap `pending_drips` and refuse to stage a second while one is unapproved).

## 9. [FIX] Missing arming listeners (IgnitionListener / UnlitDeepListener / SeventhChoiceListener / CoopPlateListener / RefusalRiteListener) — the M0 frame-break and the prologue gate have no producer, so `prologue.curatorialAllowed` is structurally stuck.
`decide.ts` reads `s.prologue?.curatorialAllowed ?? true` — the `?? true` back-compat default means that **with the listeners absent, the prologue gate is bypassed and curatorial drips fire from tick one**, skipping the intended "no clue drips before ignition" rule (B4). The flags these listeners are supposed to set (the ignition flag, `seventh_*`, the coop/refusal rite tokens) are exactly the `requires_flags` keys from #1 — so the *entire* flag-driven progression has **no in-world producer**: nothing sets `iss_caught`, `undercroft_open`, `seventh_named`, etc. Even after fixing #1/#2, the gated rows stay closed forever because no event ever sets their flag. **Fix:** these listeners are not optional polish — they are the only writers of the progression flags. Build them (or a temporary `/obs flag set` admin command) before any playtest, or the game cannot advance past M0.

## 10. [FIX] `setArcFlags` (repo.ts) — read-modify-write of `arc_state.flags` with NO optimistic guard; concurrent solves that set different flags can clobber each other.
`setArcFlags` reads `flags`, spreads `{...old, ...new}`, and unconditionally `update`s id=1. Two solves resolving near-simultaneously (Discord + in-world, the whole point of the dual surface) both read the old blob and the second write wins — the first solve's flag is **lost**. This is the flag layer that gates #1, so a lost `iss_caught` silently leaves the back-half closed. Note the Java side sets flags via its own path (or doesn't — `OracleResolver.applyOutcome` only enqueues the beat, it does NOT call `set_flags` at all — see #11). **Fix:** use a Postgres `jsonb || ` merge in a single `UPDATE ... SET flags = flags || :new` statement (atomic server-side), or an `RPC`, instead of read-modify-write.

## 11. [REDESIGN] `OracleResolver.applyOutcome` (Java) does NOT apply `set_flags` — only the TS surface sets arc flags. An in-world solve of a flag-setting puzzle advances nothing.
TS `applyOutcome` (resolve.ts) calls `setArcFlags(payload.set_flags)`. The Java `applyOutcome` (OracleResolver L210) reads only `outcome.get("beat")` and enqueues it — it **never reads `set_flags`**. So `a1z26-tick-stave` / `rosetta-ring` / `reckoning-rosetta` solved **in-world** (answer-sign) fire their unlock beat but never set `rosetta_known`/`reckoning_known`. The two surfaces are NOT equivalent despite the design claim ("a match on either surface produces the same outcome"). Players who solve at the keeper-stone instead of in Discord get a half-outcome and the progression silently desyncs by surface. **Fix:** add `set_flags` handling to Java `applyOutcome` (PATCH `arc_state.flags` via an atomic merge), OR route all flag-setting through a shared beat type the poller enacts. Until then, flag-setting puzzles MUST be Discord-only and the answer-sign must reject them.

## 12. [FIX] `SupabaseClient.countWorldAttemptsSince` uses `&limit=10000` and `.size()` to count — a busy window silently under-counts the rate-limit gate, and it pulls full rows instead of a HEAD count.
The comment (L314) admits it should use `HEAD` + `Prefer: count=exact` but "simpler here to read ids." At 10k it'll usually be fine, but it's O(rows) bandwidth on every single answer attempt on the hot path, and if the window ever exceeds 10k attempts the cap **fails open** (under-counts → never withholds). **Fix:** switch to `method=HEAD` with `Prefer: count=exact` and parse `Content-Range` (the client already does range-less reads everywhere; this is the one place a count matters for a security gate).

## 13. [FIX] `BeatQueuePoller` `UNHANDLED` result leaves the row `approved` forever — a beat type with no enactor is re-fetched and re-attempted every single poll.
`enactOnMain`: `UNHANDLED → { leave queued; do not write status }`. If a seed enqueues a beat `type` the current `RealBeatEnactor` doesn't handle (very likely given 96 GAP-TO-BUILD markers and beat types like RoomSwap/KeeperNpc that may not be wired), the poller re-fetches it on EVERY poll, hops to main, calls the enactor, gets UNHANDLED, and loops — forever, burning a main-thread hop per beat per poll. With several unhandled beats this is a steady main-thread tax. **Fix:** after K consecutive UNHANDLED attempts mark the row `deferred` (or log once and skip via an in-process "seen-unhandled" set), so an unbuilt beat type doesn't permanently churn the poller.

## 14. [SIMPLIFY] `Reveal.isHidden` / `isHiddenFrom` are correctly main-thread-only, but nothing in the read code proves callers honor it — the contract is comment-only.
`Reveal` touches `world.getPlayers()`, `rayTraceBlocks`, `getEyeLocation` — all main-thread Bukkit reads. The Javadoc says "MUST be called on the MAIN thread." `BeatQueuePoller` correctly enacts on main (`runMainSafe`), so the common path is safe. But there is no assertion (`Bukkit.isPrimaryThread()` check) guarding `Reveal`, and `Scheduler.isMainThread()` exists and is unused as a guard. Given the async-heavy design and Safety swallowing everything, an accidental async call to `Reveal` from a future beat would silently corrupt or throw-and-swallow. **Fix:** add a cheap `if (!Bukkit.isPrimaryThread()) { safety.warn(...); return false; }` at the top of `isHidden`/`isHiddenFrom` — fail safe and loud-in-logs rather than silent.

## 15. [KEEP] `name-where-never-been.ts` / `offline-skin.ts` precision gates ARE enforced in the pure policy — proof-of-absence and the separation law are real code, not just doc.
`selectCarve` genuinely blocks a carve when `visitedCells == null` (no proof-set → no carve), and `selectGlimpse` genuinely returns null when `phase==='named' && !namedApproved` and when the proposed cell collides with the player's carve claim. These are correct and well-guarded. **Caveat (FIX):** the gates are only as good as the `.run.ts` wrappers that FEED them — `name-where-never-been.run.ts` / `offline-skin.run.ts` must actually populate `visitedCells` from `player_visited_cells` and pass real `carveClaimsByPlayer`. If those wrappers are among the 96 GAP-TO-BUILD stubs (verify), the pure gate is correct but never receives real proof and either never fires (safe) or — worse — receives an empty set that *looks* like proof. Confirm the run wrappers pass `null` (not `new Set()`) when proof is genuinely absent, because an empty set means "provably never visited anywhere" and would let the carve fire on a wrong precision claim.

## 16. [FIX] `linkDiscord` (repo.ts) wildcard escape is correct, but the LIKE still scans `players.name` case-insensitively with no uniqueness guard — two players with names differing only by case both linkable to the wrong row.
The `\\%_` escape + post-assert `found.name?.toLowerCase() !== mcName.trim().toLowerCase()` is good defense. But `.maybeSingle()` on an `.ilike` that matches MULTIPLE rows (e.g. "Brann" and "brann" both exist) throws (maybeSingle errors on >1 row) rather than picking deterministically — a friend group with case-variant names hits a hard error at `/link`. **Fix:** add `.limit(1).order('id')` or a DB unique index on `lower(name)`; assert single-match explicitly.

## 17. [SIMPLIFY] `RealBeatEnactor` / beat lib — no read confirms `set_flags`-style side effects or PDC markers survive a `/reload`. The RoomSwap `swapped` PDC marker (referenced in SupabaseClient L428) is the swap's only idempotency.
If `RoomSwapBeat` relies on a block-PDC `swapped` marker and the chunk unloads or a world-edit clears it, the A→B swap can re-fire (the design explicitly chose NOT to back it with `world_paste_ledger`). For a friend group that comes and goes, chunk unload between sessions is the norm. **Fix:** verify the PDC marker is on a persistent block in a kept chunk, or back the swap with the ledger after all (the "no double-guard" rule is a premature optimization for a rare, high-blast event).

---

## If I could change ONE thing about this dimension
**Ship migration 0006 + wire `requires_flags` into both resolvers AND build the flag-producing listeners as one atomic change (#1 + #2 + #9 + #11 together).** Right now the game has a fully-authored progression spine that is simultaneously *wide open* (gated rows that ship active have no gate) and *permanently sealed* (gated rows that ship inactive have no producer to open them), with NO error surfaced because every guard fails silent. That single triad is the difference between "11 puzzles mis-behave" and "the M1→M5 story literally cannot progress and is trivially spoofable." Until a flag set in-world (a) persists atomically, (b) is read by `getOpenPuzzles`/`fetchOpenPuzzles`, and (c) is actually WRITTEN by a real listener, nothing else in the code dimension matters — the loop the whole project is built around is a no-op.
